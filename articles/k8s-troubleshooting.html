Kubernetes 故障排查速查手册

这份文档面向日常值班和线上应急，目标是在最短时间内确定故障层级：应用问题、容器问题、集群网络问题，还是节点资源问题。

1. 建立排查路径：先“面”后“点”

  1. 看整体：确认是单服务异常，还是命名空间级/集群级故障。
  2. 看对象状态：Deployment、Pod、Service、Ingress 是否健康。
  3. 看事件与日志：Events 是第一现场，日志是业务证据。
  4. 看节点与网络：CNI、CoreDNS、kube-proxy 异常会造成“大面积不可达”。

2. 高频故障场景与处理

2.1 Pod 卡在 Pending

  • 资源不足：CPU/内存请求过高，调度器无法分配。
  • 节点污点：未配置 tolerations。
  • PVC 未绑定：存储类、容量、访问模式不匹配。
kubectl get pod -n prod
kubectl describe pod my-app-xxx -n prod
kubectl get events -n prod --sort-by=.lastTimestamp

2.2 Pod 重启频繁（CrashLoopBackOff）

  • 启动命令错误或依赖服务未就绪。
  • 配置中心参数缺失、密钥挂载错误。
  • 内存限制太小，触发 OOMKilled。
kubectl logs my-app-xxx -n prod --previous
kubectl describe pod my-app-xxx -n prod | grep -E "Reason|OOMKilled|Exit Code"

2.3 服务不可达（Service/Ingress）

  • Service selector 与 Pod label 不一致。
  • 容器监听端口与 targetPort 不匹配。
  • Ingress 后端服务名或端口配置错误。
kubectl get svc,ep -n prod
kubectl describe ingress app-ing -n prod

3. 生产环境建议

  • 统一探针策略：startupProbe + livenessProbe + readinessProbe。
  • 为关键服务配置 PDB，避免节点维护时全量中断。
  • 启用资源配额与限制，防止“邻居噪声”。
  • 将 kubectl 常用排查命令沉淀为脚本，减少手动误操作。

4. 值班应急模板

建议团队固定采用「10分钟止血、30分钟定界、2小时复盘」机制：先恢复可用性，再查根因，最后更新 Runbook 与告警阈值。
