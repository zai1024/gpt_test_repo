MySQL 索引优化实践：从慢 SQL 到稳定低延迟

索引优化的核心不是“多建索引”，而是围绕查询路径减少扫描行数、避免回表、降低随机 IO，并在写入成本和读取收益之间找到平衡。

1. 先理解 B+Tree 的代价模型

  • 主键索引叶子节点存整行数据；二级索引叶子节点存索引列+主键。
  • 使用二级索引查询非覆盖字段时，需要回表。
  • 范围查询会让后续列无法充分利用复合索引。

2. 慢 SQL 诊断流程

  1. 从慢日志挑选 Top SQL（按总耗时/平均耗时）。
  2. 用 EXPLAIN 查看 type、rows、filtered、extra。
  3. 对照业务访问模式决定是否改 SQL 或调索引。
EXPLAIN SELECT id, title, status
FROM post
WHERE author_id = 1024 AND status = 1
ORDER BY created_at DESC
LIMIT 20;

3. 关键优化规则

3.1 复合索引按“过滤度+排序”设计

如果查询固定是 author_id + status + created_at，可建立 (author_id, status, created_at)，同时覆盖 select 字段以减少回表。

3.2 避免索引失效

  • 避免在索引列上使用函数或隐式类型转换。
  • 尽量减少前导模糊查询（LIKE '%abc'）。
  • 避免 OR 连接多个未命中索引的条件。

3.3 索引不是越多越好

每个新增索引都会增加写入成本、占用缓存与磁盘。需要定期清理冗余索引和低命中索引。

4. 生产建议

  • 对热点查询建立“索引基线”，变更前后压测对比。
  • 为大表变更使用在线 DDL 工具，避免长时间锁表。
  • 结合 APM 指标监控 p95/p99，防止“平均值掩盖抖动”。
